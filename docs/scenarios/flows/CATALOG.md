# Каталог пользовательских инструкций Flows

Рабочий документ (не публикуется в дереве документации). Определяет полный набор
инструкций сервиса Flows: судьбу текущих сценариев, новую taxonomy, единый сквозной
пример и карточки будущих сценариев. Реализация E2E-тестов — отдельный этап.

Стандарт качества: [`.cursor/skills/documentator/SKILL.md`](../../../.cursor/skills/documentator/SKILL.md).

## 1. Сквозной пример (единый для всех инструкций)

Интернет-магазин садовых товаров **«Зелёный сад»** собирает ИИ-помощника для клиентов и операций.
Одни и те же сущности переходят из сценария в сценарий — пользователь видит эволюцию одного реального агента.

| Сущность | Значение в инструкциях |
|---|---|
| Агент (flow) | «Помощник Зелёного сада» |
| Ветка эксперимента | «Летние скидки» |
| Файлы | «Каталог-весна-2026.pdf», «Условия-доставки.pdf» |
| Переменные | приветствие покупателя, адрес поддержки `support@zeleniy-sad.ru`, город склада «Воронеж» |
| Канал | Telegram-бот «@zeleniy_sad_bot» |
| Внешний сервис | сервис отслеживания заказов «Где мой заказ» |
| Очередь операторов | «Поддержка клиентов» (сложные обращения), «Возвраты» (спорные возвраты) |
| Оператор | Марина — сотрудник поддержки, работает в разделе задач |
| Второй агент | «Агент возвратов» (для handoff между агентами) |

Правила именования в тексте инструкций:
- Только человеческие названия и подписи интерфейса.
- Запрещены `node_id`, `payload`, `seed`, `slug`, `namespace`, `runtime` и подобный жаргон.
- Сообщения, письма, имена файлов — правдоподобные, вписанные в контекст магазина.

## 3. Новая taxonomy Flows

Правка [`docs/scenarios/taxonomy.yaml`](../taxonomy.yaml), `services.flows`.

`featured_slug: flows-home-tour`.

Теги (порядок = прогрессия):

| Tag | label_ru | label_en | order |
|---|---|---|---|
| `getting-started` | Первые шаги | Getting started | 0 |
| `editor` | Редактор графа | Graph editor | 1 |
| `nodes` | Возможности агента | Agent capabilities | 2 |
| `data` | Данные и переменные | Data and variables | 3 |
| `execution` | Тестирование и отладка | Testing and debugging | 4 |
| `triggers` | Триггеры | Triggers | 5 |
| `api` | API и доступ | API and access | 6 |
| `operations` | Публикация и управление | Publishing and operations | 7 |
| `evaluation` | Проверка качества | Quality evaluation | 8 |
| `setup` | Подключения компании | Company connections | 9 |

Изменения: тег `chat` схлопывается в `execution`; тег `agent-download` удаляется.

Learning path **flows** (простое → сложное):
`flows-home-tour` → `create-first-agent` → `agent-focus-vs-canvas` →
`configure-agent-answers` → `attach-skills-to-agent` → `test-agent-in-chat` →
`skills-unlock-in-chat` → `add-agent-tools` → `publish-and-operate`.

Learning path **flows-skills**:
`manage-agent-skills` → `attach-skills-to-agent` → `skills-unlock-in-chat` →
`duplicate-and-edit-skill`.

Skills остаются в тегах `nodes` и `execution` (отдельный taxonomy-tag `skills` не вводим).

Кросс-сервисный блок «Операторы и HITL» (раздел 4a) частично живёт в сервисе
**worktracker**: карточки B1–B5 получают `service: worktracker` и новый tag `operators`
(label_ru «Операторы», label_en «Operators»). Flows-стороны блока (A1–A5) используют
существующие теги `nodes` и `execution`. Learning path **worktracker/operators**:
`setup-operator-queue` → `operator-inbox-single-reply` → `operator-takeover-dialog` →
`route-and-reassign-tasks` (+ опц. `track-work-on-board`). При реализации первых
операторских сценариев в `docs/scenarios/taxonomy.yaml` добавляется `services.worktracker`
с этим тегом (если сервиса там ещё нет).

## 4. Карточки сценариев

Формат карточки:
- **Задача / проблема / результат** — три обязательных блока `description`.
- **Шаги** — 4–7 пользовательских этапов.
- **Демонстрация** — чем доказываем результат.
- **Фичи** — покрываемый функционал UI.

### Этап 1. Первые шаги (getting-started)

#### 1.1 `getting-started/flows-home-tour`
- Title: «Знакомство с Flows: главная и каталог агентов» / "Getting to know Flows: home and agent catalog"
- Для чего: освоиться на главной Flows и научиться находить нужного агента.
- Проблема: новый пользователь не понимает, где список агентов, как открыть чат или редактор.
- Результат: открыт «Помощник Зелёного сада» и понятно, куда нажимать дальше.
- Шаги: 1) открыть Flows и осмотреть главную (счётчики, быстрые действия); 2) найти агента через поиск каталога; 3) раскрыть карточку агента и понять кнопки «Чат» и «Редактор»; 4) посмотреть недавние диалоги; 5) открыть чат агента как демонстрацию.
- Демонстрация: открытый чат «Помощника Зелёного сада».
- Фичи: метрики главной, поиск каталога, карточка flow, недавние сессии, CTA скачивания LinnexAgent.

#### 1.2 `getting-started/create-first-agent`
- Title: «Создаём первого агента из шаблона» / "Create your first agent from a template"
- Для чего: создать собственного агента, не собирая граф с нуля.
- Проблема: непонятно, с какого шаблона начать и какие поля заполнять.
- Результат: «Помощник Зелёного сада» создан и открыт в редакторе с готовыми нодами.
- Шаги: 1) нажать создание из каталога; 2) выбрать подходящий шаблон (обычный агент / граф / оркестратор / код / внешний); 3) заполнить идентификатор, название, описание; 4) создать и попасть в редактор; 5) убедиться, что на канве есть стартовые ноды.
- Демонстрация: редактор с готовой канвой нового агента.
- Фичи: мастер создания, пресеты (react/graph/multi/code/external), Store bundles, поля id/name/description.

#### 1.3 `getting-started/chat-with-lara`
- Title: «Чат с Lara — помощником платформы» / "Chat with Lara — the platform assistant"
- Для чего: спросить у Lara про платформу, не настраивая своего агента.
- Результат: ответ Lara в чате.
- Шаги: 1) открыть главную Flows; 2) открыть чат Lara; 3) задать простой вопрос; 4) увидеть ответ (и при необходимости чипы Skill).
- Демонстрация: диалог с ответом Lara.
- Фичи: route `/flows/chat/lara`, platform-chat, skill load chips (опционально).

### Этап 2. Редактор графа (editor)

#### 2.0 `editor/agent-focus-vs-canvas`
- Title: «Студия и схема: два режима редактора» / "Studio and canvas: two editor modes"
- Для чего: понять разницу студии и канвы и переключаться между ними.
- Результат: одно изменение промпта видно в обоих режимах.
- Шаги: 1) открыть single-llm агента в студии; 2) изменить промпт; 3) переключить на канву; 4) открыть ту же ноду; 5) вернуться в студию.
- Демонстрация: промпт сохранён после переключения режимов.
- Фичи: `flows-agent-focus-studio`, layout toggle, `flows-flow-canvas` (только eligible single-llm).

#### 2.1 `editor/configure-agent-answers` (merge add-llm-node + edit-llm-flow)
- Title: «Настраиваем ответы агента: промпт и модель» / "Shape agent answers: prompt and model"
- Для чего: задать поведение агента и модель, затем изменить и сохранить.
- Проблема: агент отвечает не так, как нужно магазину; непонятно, где менять инструкцию и модель.
- Результат: агент отвечает вежливо от лица «Зелёного сада», изменения опубликованы и видны после переоткрытия.
- Шаги: 1) открыть LLM-ноду; 2) написать промпт с подстановкой имени покупателя; 3) выбрать модель, температуру и лимит ответа; 4) опубликовать черновик; 5) изменить промпт (добавить упоминание доставки) и снова опубликовать; 6) переоткрыть агента и убедиться, что настройки сохранились.
- Демонстрация: повторно открытая нода с сохранённым обновлённым промптом.
- Фичи: LLM-нода, prompt-editor (`{переменные}`, файлы, preview), выбор провайдера/модели/температуры/лимитов, Publish, draft/published.

#### 2.2 `editor/branch-by-condition`
- Title: «Развилка в диалоге: условия на связях» / "Branch the dialog with edge conditions"
- Для чего: направлять покупателя по разным веткам (заказ vs возврат).
- Проблема: агент обрабатывает все запросы одинаково, хотя сценарии разные.
- Результат: запрос о заказе и запрос о возврате идут по разным путям графа.
- Шаги: 1) добавить вторую ветвь обработки; 2) соединить ноды связью порт→порт; 3) задать условие на связи (по ключевому слову «возврат»); 4) настроить, ждать ли одну или все входящие связи; 5) запустить тест и увидеть подсвеченный путь.
- Демонстрация: тестовый запуск с подсветкой сработавшей ветки.
- Фичи: wiring на канве, edge condition (простое + код), incoming policy ANY/ALL, подсветка пути при прогоне.

#### 2.3 `editor/organize-large-graph` (merge dataflow-wiring + dataflow-problems)
- Title: «Наводим порядок в большом графе» / "Keep a large graph readable"
- Для чего: держать сложного агента понятным и находить ошибки связей.
- Проблема: граф разрастается, теряются связи данных и появляются проблемные места.
- Результат: граф аккуратно размещён, заметки поясняют блоки, проблемные связи найдены и исправлены.
- Шаги: 1) включить авто-раскладку и подогнать масштаб; 2) добавить поясняющие заметки к блокам; 3) включить показ связей данных; 4) открыть список проблем dataflow и перейти к проблемной ноде; 5) исправить связь и убедиться, что предупреждение исчезло.
- Демонстрация: панель проблем без ошибок после исправления.
- Фичи: sticky notes, zoom/fit/100%, undo/redo, select/pan, smart guides, data wires toggle, dataflow problems flyout → jump to node, авто-раскладка, shortcuts.

### Этап 3. Возможности агента / типы нод (nodes)

#### 3.0a `nodes/manage-agent-skills`
- Title: «Создаём Skill «Возврат заказа»» / "Create the Order return Skill"
- Для чего: завести процедуру в библиотеке Skills.
- Результат: Skill с name/description/body в библиотеке.
- Шаги: 1) открыть Skills; 2) создать; 3) заполнить id/name/description; 4) написать body; 5) сохранить и увидеть в списке.
- Фичи: `/flows/skills`, create modal, skill editor, how-it-works.

#### 3.0b `nodes/attach-skills-to-agent`
- Title: «Подключаем Skill к агенту» / "Attach a Skill to the agent"
- Для чего: привязать Skill к ноде в режиме Инструменты.
- Результат: чип Skill на ноде; в Структурированном секция скрыта.
- Шаги: 1) Tools mode; 2) Add skill; 3) чип; 4) edit modal с чипа; 5) Structured hides Skills; 6) вернуться в Tools.
- Фичи: agent_skills на llm_node, picker, meta-tools load не в standing Tools.

#### 3.0c `nodes/duplicate-and-edit-skill`
- Title: «Дублируем и правим Skill» / "Duplicate and edit a Skill"
- Для чего: скопировать процедуру под другой кейс.
- Результат: копия в библиотеке с новым id.
- Шаги: 1) открыть Skill; 2) Duplicate; 3) новый id/name; 4) править body; 5) увидеть копию в списке.
- Фичи: duplicate panel, replace attach (опционально с chip modal).

#### 3.1 `nodes/add-agent-tools`
- Title: «Даём агенту инструменты» / "Give the agent tools"
- Для чего: научить агента выполнять действия, а не только отвечать текстом.
- Результат: агент сам вызывает инструмент и использует результат в ответе.
- Шаги: 1) переключить ноду в режим инструментов; 2) выбрать инструмент из библиотеки; 3) настроить встроенный инструмент; 4) задать пределы цикла рассуждения; 5) запустить и увидеть вызов инструмента в ответе.
- Демонстрация: ответ агента с видимым вызовом инструмента.
- Фичи: LLM-нода Tools mode, library picker, embedded tool config, tool create (inline), loop_mode/max_iterations/exit_tool.

#### 3.2 `nodes/structured-answer`
- Title: «Строгий JSON-ответ агента» / "Get a strict JSON answer"
- Для чего: получать ответ в заданной структуре для дальнейшей обработки.
- Результат: агент возвращает данные заказа строгим JSON по схеме.
- Шаги: 1) переключить ноду в режим структурированного вывода; 2) описать схему полей ответа; 3) настроить, какие сообщения видит нода; 4) запустить; 5) открыть состояние и проверить структуру.
- Демонстрация: панель состояния с валидным JSON-ответом.
- Фичи: output mode Structured Output, output_schema, messages_filter, просмотр State.

#### 3.3 `nodes/process-with-code`
- Title: «Обрабатываем данные кодом» / "Process data with a code node"
- Для чего: посчитать или преобразовать данные внутри агента.
- Результат: нода кода считает сумму заказа со скидкой и передаёт дальше.
- Шаги: 1) добавить ноду кода; 2) написать код и описать входные параметры; 3) проверить и выполнить код; 4) соединить с остальным графом; 5) запустить и увидеть результат вычисления.
- Демонстрация: результат вычисления в тестовом прогоне.
- Фичи: code node editor/workbench, language, parameters_schema, validate, execute, docs, drop файла, wiring.

#### 3.4 `nodes/call-order-tracking-api`
- Title: «Подключаем сервис отслеживания заказов» / "Connect an order tracking service"
- Для чего: получать статус заказа из внешнего сервиса.
- Результат: агент показывает покупателю актуальный статус его заказа.
- Шаги: 1) добавить ноду внешнего сервиса; 2) указать метод, адрес и заголовки; 3) сопоставить номер заказа со входом запроса; 4) сопоставить статус из ответа; 5) запустить и увидеть статус в ответе.
- Демонстрация: ответ агента со статусом заказа из сервиса.
- Фичи: external_api node (method/url/headers/body/timeout), input/output mapping.

#### 3.5 `nodes/connect-mcp-tool` (rewrite mcp-workflow)
- Title: «Подключаем MCP-инструмент» / "Connect an MCP tool"
- Для чего: расширить агента инструментами из MCP-сервера.
- Результат: агент вызывает инструмент MCP-сервера и использует ответ.
- Шаги: 1) открыть управление MCP-серверами; 2) добавить сервер или установить из каталога; 3) синхронизировать инструменты и проверить подключение; 4) добавить инструмент MCP в агента; 5) запустить и увидеть результат вызова.
- Демонстрация: ответ агента с результатом инструмента MCP.
- Фичи: MCP servers modal (add http/sse, auth presets, sync tools, test, catalog install), mcp node / llm_node MCP tool.

#### 3.6 `nodes/notify-in-telegram`
- Title: «Отправляем ответ в Telegram» / "Send the answer to Telegram"
- Для чего: доставлять сообщение покупателю в Telegram.
- Результат: агент отправляет уведомление в бот «@zeleniy_sad_bot».
- Шаги: 1) добавить ноду канала; 2) выбрать Telegram и указать настройки бота; 3) сопоставить получателя и текст; 4) соединить с графом; 5) запустить и убедиться в отправке.
- Демонстрация: подтверждение отправки сообщения в канал.
- Фичи: channel node (telegram/email/webhook), action, channel_config, input mapping recipient/text.

#### 3.7 `nodes/compose-orchestrator`
- Title: «Собираем агента из под-агентов» / "Compose an orchestrator from sub-agents"
- Для чего: разделить сложную задачу на специализированных под-агентов.
- Результат: главный агент направляет запрос под-агенту доставки или возвратов.
- Шаги: 1) создать агента-оркестратора; 2) добавить ноду вложенного агента; 3) сопоставить вход и выход под-агента; 4) подключить под-агента как инструмент; 5) запустить и проследить делегирование.
- Демонстрация: прогон, где оркестратор вызывает под-агента.
- Фичи: multi preset, flow node (subflow) + mapping, flow-as-tool, react_role.

#### 3.8 `nodes/call-remote-agent`
- Title: «Вызываем внешнего агента» / "Call a remote agent"
- Для чего: использовать агента другой компании по протоколу A2A.
- Результат: агент получает ответ от внешнего агента-партнёра.
- Шаги: 1) добавить ноду внешнего агента; 2) указать адрес или идентификатор агента и ветку; 3) задать заголовки авторизации; 4) соединить с графом; 5) запустить и увидеть ответ внешнего агента.
- Демонстрация: ответ, полученный от внешнего агента.
- Фичи: remote_flow node (URL или flow_id+branch, auth headers).

#### 3.9 `nodes/add-answer-review`
- Title: «Добавляем самопроверку ответа» / "Add an answer self-review"
- Для чего: не отдавать покупателю ответ, не прошедший проверку качества.
- Результат: слабый ответ блокируется и переделывается до выдачи.
- Шаги: 1) добавить ноду проверки; 2) настроить критика и критерии; 3) задать порог и реакцию на нарушения; 4) соединить после основной ноды; 5) запустить и увидеть блокировку слабого ответа.
- Демонстрация: прогон, где проверка отклонила и улучшила ответ.
- Фичи: reflection node, critic policy (gate/target/min_confidence/criteria/severities).

#### 3.10 `nodes/escalate-to-operator`

## 4a. Блок «Операторы и HITL» (работа flow с людьми)

Сквозной сюжет блока: «Помощник Зелёного сада» умеет отвечать сам, но по сложным
обращениям (спорный возврат, нестандартная доставка) подключает живого оператора
Марину через раздел задач (worktracker). Пользователь видит в чате, что его вопрос
передан человеку; Марина берёт задачу из очереди, отвечает или ведёт диалог; агент
продолжает работу с учётом ответа оператора.

### Термины для текста инструкций (без жаргона)

| Реальный термин в UI/тексте | Технический смысл (в тексте не писать) |
|---|---|
| «Передача оператору», «нужен человек» | hitl_node / tool `hitl_operator_task`, `OperatorTaskInterrupt` |
| «Один ответ оператора» | `handoff_mode = single_reply` |
| «Оператор ведёт диалог» / «перехват» | `handoff_mode = takeover` |
| «Очередь поддержки» | `WorkQueue` + `work_queue_slug` |
| «Задача оператора», «карточка задачи» | `WorkItem(kind=operator_handoff)` |
| «Раздел задач», «входящие», «доска» | worktracker SPA (inbox / board / queues) |
| «Взять задачу» | claim |
| «Завершить / закрыть задачу» | complete + resolution |
| «Фоновая задача команде» | `work_item_create(blocking=false)` |

### Роли и сервисы (важно для реализации тестов)

Блок пересекает два сервиса. У каждой карточки указан `service` и `tag` для будущего
`@pytest.mark.scenario`:

- **flows** (сторона конструктора и покупателя): настройка hitl-ноды, ожидание в чате,
  фоновая задача, наблюдение передачи в истории выполнения.
- **worktracker** (сторона оператора и администратора): очереди, входящие, работа с
  задачей, доски.

Прогрессия блока (простое → сложное):
`escalate-to-operator` → `setup-operator-queue` → `operator-inbox-single-reply` →
`customer-waits-for-operator` → `operator-takeover-dialog` → `route-and-reassign-tasks` →
`agent-logs-background-task` → `trace-operator-handoff`.

### Сторона flows (конструктор и покупатель)

#### A1 `flows · nodes/escalate-to-operator`
Совпадает с карточкой 3.10 (входная точка блока). Здесь — настройка ноды передачи
оператору в режиме «один ответ»: очередь «Поддержка клиентов», заголовок задачи,
сообщение покупателю на время ожидания.

#### A2 `flows · nodes/agent-decides-to-escalate`
- Title: «Агент сам зовёт оператора» / "Let the agent call an operator itself"
- Для чего: не рисовать жёсткую развилку, а позволить агенту решать, когда нужен человек.
- Проблема: заранее неизвестно, какой запрос окажется сложным; фиксированная нода срабатывает не всегда к месту.
- Результат: когда агент не уверен в ответе о возврате, он сам передаёт диалог в очередь «Поддержка клиентов».
- Шаги: 1) открыть LLM-ноду в режиме инструментов; 2) добавить инструмент «передать оператору»; 3) указать очередь и режим «один ответ»; 4) в инструкции агента описать, когда звать человека; 5) в тестовом чате задать сложный вопрос и увидеть передачу оператору.
- Демонстрация: чат, где агент сам инициировал ожидание оператора.
- Фичи: llm_node Tools mode, встроенный tool `hitl_operator_task` (question/task_title/assignee_queue/handoff_mode).
- Отличие от A1: A1 — детерминированная нода на графе; A2 — решение самого агента.

#### A3 `flows · execution/customer-waits-for-operator`
- Title: «Что видит покупатель, пока ждёт оператора» / "What the customer sees while waiting for an operator"
- Для чего: показать конструктору поведение чата глазами покупателя при передаче человеку.
- Проблема: непонятно, зависает ли чат, можно ли писать дальше и как приходит ответ человека.
- Результат: покупатель видит понятное сообщение об ожидании, ссылку на задачу и получает ответ оператора прямо в чате.
- Шаги: 1) открыть чат агента; 2) довести диалог до передачи оператору; 3) увидеть плашку ожидания и карточку задачи; 4) (режим диалога) продолжить писать оператору; 5) дождаться ответа оператора в ленте чата.
- Демонстрация: сообщение оператора появилось в чате покупателя.
- Фичи: chat input-required (operator_task), плашка ожидания, `<platform-work-item-badge>`, артефакты `operator_reply`/`operator_files`, резюмирование диалога после ответа.

#### A4 `flows · nodes/agent-logs-background-task`
- Title: «Агент ставит фоновую задачу команде» / "Agent files a background task for the team"
- Для чего: зафиксировать поручение людям, не останавливая диалог с покупателем.
- Проблема: некоторые действия (перезвонить, проверить остаток) нужны людям, но покупателя нельзя заставлять ждать.
- Результат: агент создаёт задачу в очереди и сразу продолжает отвечать покупателю.
- Шаги: 1) в LLM-ноде добавить инструмент создания задачи; 2) выбрать очередь-получателя и оставить режим «без ожидания»; 3) описать, что писать в задачу; 4) запустить диалог; 5) убедиться, что агент ответил сразу, а задача появилась в разделе задач.
- Демонстрация: ответ агента без паузы + новая фоновая задача в очереди.
- Фичи: tool `work_item_create` (assignee_type queue/user, `blocking=false`), отличие fire-and-forget от HITL-паузы.

#### A5 `flows · execution/trace-operator-handoff`
- Title: «Смотрим передачу оператору в истории выполнения» / "See the operator handoff in the run history"
- Для чего: разобрать после прогона, где и как агент передавал диалог человеку.
- Проблема: по одному чату не видно, в какой момент и в какую очередь ушла задача.
- Результат: в истории выполнения найдены события передачи и возврата, открыта связанная задача.
- Шаги: 1) открыть историю выполнения диалога; 2) найти событие передачи оператору; 3) открыть карточку связанной задачи по значку; 4) найти событие возврата после ответа оператора; 5) сделать вывод о ходе диалога.
- Демонстрация: событие передачи с карточкой задачи и последующим возвратом.
- Фичи: durable history (handoff_requested/handoff_resumed), work-item badge, deep-link в раздел задач.

### Сторона worktracker (оператор и администратор)

#### B1 `worktracker · operators/setup-operator-queue`
- Title: «Готовим очередь поддержки» / "Set up a support queue"
- Для чего: собрать очередь, в которую агенты будут передавать сложные обращения.
- Проблема: без очереди и назначенных людей задачи агента некому разбирать.
- Результат: создана очередь «Поддержка клиентов», в неё добавлена оператор Марина.
- Шаги: 1) открыть раздел очередей; 2) создать очередь с названием «Поддержка клиентов»; 3) открыть очередь; 4) добавить участника-оператора; 5) убедиться, что участник видит входящие очереди.
- Демонстрация: очередь с участником и её входящими.
- Фичи: queues page, создание очереди (name + slug), queue detail, добавление/удаление участников (user/agent).

#### B2 `worktracker · operators/operator-inbox-single-reply`
- Title: «Оператор берёт задачу и отвечает один раз» / "Operator claims a task and replies once"
- Для чего: показать базовый цикл: агент передал — человек ответил — агент продолжил.
- Проблема: оператор не понимает, откуда приходят задачи агента и как вернуть ответ в диалог.
- Результат: Марина взяла задачу из очереди, ответила и закрыла её — агент продолжил диалог с покупателем.
- Шаги: 1) открыть входящие (можно из Flows по кнопке «Оператор»); 2) найти задачу от агента в очереди; 3) взять задачу себе; 4) прочитать контекст обращения; 5) завершить задачу с ответом покупателю; 6) убедиться, что диалог агента продолжился.
- Демонстрация: закрытая задача и продолжение диалога в чате покупателя.
- Фичи: inbox (assigned + unclaimed по очередям), claim, карточка задачи (контекст, links flow_session), complete + resolution, resume flow.
- Вход из Flows: quick action «Operator / HITL», строка готовности «Открытые задачи» с счётчиком.

#### B3 `worktracker · operators/operator-takeover-dialog`
- Title: «Оператор ведёт живой диалог с покупателем» / "Operator takes over the live dialog"
- Для чего: полностью перехватить общение, когда нужен несколько-шаговый разговор с человеком.
- Проблема: одного ответа мало — по спорному возврату нужно уточнять детали в переписке.
- Результат: Марина переписывается с покупателем в реальном времени, прикладывает файл и завершает задачу — агент подхватывает итог диалога.
- Шаги: 1) взять задачу режима «диалог» из очереди «Возвраты»; 2) написать покупателю уточняющий вопрос в ленте задачи; 3) увидеть ответ покупателя из чата; 4) приложить документ (форму возврата); 5) завершить задачу с решением; 6) убедиться, что агент продолжил с учётом всего диалога.
- Демонстрация: переписка оператор↔покупатель и корректное продолжение агента.
- Фичи: takeover, activity thread (comment role=operator, файлы), встречные сообщения покупателя как комментарии role=user, complete со сборкой всего диалога, стрим operator_reply/operator_files в чат.

#### B4 `worktracker · operators/route-and-reassign-tasks`
- Title: «Маршрутизация и переназначение задач» / "Route and reassign operator tasks"
- Для чего: направлять разные обращения в разные очереди и передавать задачу другому исполнителю.
- Проблема: возвраты и общие вопросы смешиваются; иногда задачу нужно отдать коллеге или агенту.
- Результат: возвраты идут в очередь «Возвраты», а конкретную задачу Марина переназначает коллеге или на «Агента возвратов».
- Шаги: 1) увидеть, что разные ноды передают в разные очереди; 2) открыть задачу; 3) переназначить её другому оператору; 4) при необходимости назначить исполнителем агента; 5) убедиться, что задача ушла нужному исполнителю (пришло уведомление).
- Демонстрация: задача с новым исполнителем и уведомление о назначении.
- Фичи: несколько work_queue_slug на разных hitl-нодах, assignee picker, reassign на user/queue/agent-flow, hook assigned (запуск агента-исполнителя), уведомление WORK_ITEM_ASSIGNED.

#### B5 `worktracker · operators/track-work-on-board` (опционально)
- Title: «Ведём задачи на доске» / "Track operator work on a board"
- Для чего: держать поток обращений под контролем на канбан-доске.
- Проблема: список входящих не показывает общий статус потока задач.
- Результат: задачи разложены по колонкам, видно, что в работе и что закрыто.
- Шаги: 1) открыть доску; 2) выбрать или создать доску потока поддержки; 3) перетащить задачу в колонку «В работе»; 4) настроить колонки под процесс; 5) убедиться, что статус задачи обновился везде.
- Демонстрация: карточка задачи, перемещённая между колонками.
- Фичи: board page (drag cards/columns), board picker, create/settings modals, realtime обновление.
